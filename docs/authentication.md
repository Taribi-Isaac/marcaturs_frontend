# Participant authentication (MH-GATE-006)

## Token / session lifecycle (MH-GATE-008 / MH-BE-047)

Authoritative backend policy: [`backend/docs/authentication-token-policy.md`](../../backend/docs/authentication-token-policy.md).

Summary for SPA engineers:

- First-party auth is **Sanctum cookie session + CSRF** (`credentials: 'include'`). Do not rely on storing the login response Bearer PAT in `localStorage`.
- **PAT lifetime** (when Bearer is used) = **7 days** (`SANCTUM_TOKEN_EXPIRATION_MINUTES=10080`).
- Login/register revoke prior PATs and issue one new `auth` PAT.
- Change password keeps the **current** session/token and revokes other PATs.
- Password reset revokes all PATs and clears the user’s database `sessions` rows.
- `401` → treat as logged out; `403` → do **not** force logout.
- No automatic token refresh and no JWT.

## 401 vs 403

| Status  | Meaning                                                                                                               | Participant SPA behavior                                                                                                                                                                       |
| ------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **401** | Missing, invalid, expired, or revoked credentials                                                                     | Treat as logged out → `/login`                                                                                                                                                                 |
| **403** | Authenticated but not permitted (wrong role, account blocked/restricted product action, email unverified product API) | **Do not** force logout. Role mismatch → `/forbidden`. Suspended/banned → `/account-blocked`. Email unverified → verification-required UI. Transient/non-401 me failures → session recovery UI |

Password change keeps the **current** Sanctum token/session and does **not** regenerate the SPA session cookie (avoids concurrent-request races that looked like random logout).

## Email verification gate

Architecture:

```text
Email Verification ≠ Participant Verification ≠ Certification ≠ Reputation
```

- New BUSINESS/AMBASSADOR registrations receive a verification email and can authenticate, but `email.verified` middleware blocks product APIs until `email_verified_at` is set.
- Allow-listed while unverified: `/auth/me`, logout, change-password, resend verification.
- Admin staff are exempt.
- Seed/demo accounts are created verified. Existing unverified database rows are gated until they verify (no fabricated timestamps).

## Password reset (MH-FE-022)

Participant SPA routes:

| Route                             | Purpose                                                     |
| --------------------------------- | ----------------------------------------------------------- |
| `/forgot-password`                | Request a reset email (`POST /api/v1/auth/forgot-password`) |
| `/reset-password?token=…&email=…` | Submit a new password (`POST /api/v1/auth/reset-password`)  |

Email links are generated by `ResetPasswordNotification` as `{FRONTEND_URL}/reset-password?token=…&email=…`.

Behaviour:

- Missing `token` or `email` → incomplete-link state with CTA to `/forgot-password`.
- Invalid/expired/reused token → `422 business_validation` → unavailable-link state (no account enumeration).
- Success → clear success panel and **Sign in** CTA (no automatic session).
- Forgot-password success uses the backend anti-enumeration message.
- `/reset-password` is **not** wrapped in `GuestOnly`, so email links still work when an SPA session already exists in the browser.

Local UAT: `node scripts/mh-fe-022-password-reset-uat.mjs` (requires API, FE, Redis worker drain via the script).

## Payment return URLs

`PaystackReturnUrl` builds browser returns from `FRONTEND_URL` + product path (fallback: `PAYSTACK_CALLBACK_URL`). Local participant Vite uses port **5180** — set `FRONTEND_URL` accordingly.
